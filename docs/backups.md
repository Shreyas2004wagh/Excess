# Encrypted backups and recovery

Code rollback does not recover database records. Excess now has a streaming encrypted export, an isolated restore drill, a manual opt-in GitHub workflow, and synthetic CI recovery tests. **Live backups and a recurring schedule are not enabled by committing these files.** An export is not considered a tested recovery point until its restore drill passes.

## Safety boundaries

- PostgreSQL is authoritative for accounts, money, orders, positions, audit records, and Prisma migration history. Redis is not a financial backup source.
- Backup reads use an explicitly supplied **direct** PostgreSQL 17 connection, never an implicit application `.env` or the pooled Neon hostname. Remote connections require TLS. No migrations, resets, lock termination, or database writes are run by the exporter.
- The export and fingerprints share an exported repeatable-read snapshot. Trading can continue while the backup runs; later committed writes are intentionally not included. Avoid concurrent schema migrations: the dump has a five-second lock wait limit, and reads have bounded timeouts.
- All ordinary tables in `public` are fingerprinted, including currently empty tables. The tool requires the core financial tables and nonempty migration history. Additional user schemas, partitioned/foreign tables, and materialized views are unsupported and fail closed until coverage is extended.
- `pg_dump` streams directly into **age public-key encryption**: no plaintext dump file is created during export. The verification manifest (row counts/hashes, reconciliation results, time, and encrypted-dump checksum) is encrypted separately. A completion marker is written last. Failed exports remove only their own newly created output directory.
- The backup workflow receives a public recipient, **not** the private decryption identity. Do not add that identity to GitHub, Render, Vercel, the repository, or an application environment file.
- A restore drill accepts **no target database URL**. It uses a fresh PostgreSQL 17 Docker container: no network, published ports, host mounts, production secrets, or application processes. Its database is RAM-backed and bounded to 512 MiB; encrypted and decrypted dump files are capped at 512 MiB too. The container is capped at 1 GiB RAM, one CPU, and 256 processes. Larger databases require a reviewed capacity change, not a fallback to the live database.
- Complete age authentication happens **before** any archived SQL executes. The decrypted dump is temporarily stored in a mode-0600 file under a private OS temporary directory. Use an encrypted local disk, not a shared temp directory. Normal errors and handled interrupts remove temporary plaintext and the drill's own container. A hard kill, host crash, or unavailable Docker daemon can leave private scratch data or a container; inspect and remove only the specific `excess-restore-<UUID>` resources from that operation. Secure erasure of SSD blocks is not guaranteed.
- Encryption does not prove who created a backup: anyone with a public recipient can encrypt a file. Restore only a trusted export whose workflow/repository/run provenance you have checked. PostgreSQL archives can execute SQL chosen by the source; isolation is intentional. Do not run untrusted archives against any valuable database.
- The archive covers `public`, not cluster roles/passwords, Redis, Clerk identities, provider configuration, application secrets, or uploaded files. Preserve configuration and keys separately. Restoring PostgreSQL does not recreate deleted Clerk identities.

## Prerequisites and key ownership

Use Node.js 22+, Docker, the **PostgreSQL 17 client tools** (`psql`, `pg_dump`), `age`, and `age-keygen`. The tools reject a different dump-client/server major version rather than assuming compatibility. The CI helper installs the official PostgreSQL 17 client and age on Ubuntu 24.04.

For macOS, install the tools without starting another PostgreSQL server:

```bash
brew install age postgresql@17
export BACKUP_PG_BIN_DIR="$(brew --prefix postgresql@17)/bin"
```

The operator should generate the long-lived identity locally, outside this checkout, using restrictive permissions:

```bash
umask 077
mkdir -p "$HOME/.config/excess-recovery"
age-keygen -o "$HOME/.config/excess-recovery/backup.agekey"
age-keygen -y "$HOME/.config/excess-recovery/backup.agekey"
```

The last command prints the **public** `age1…` recipient. Keep the private file in a password manager or encrypted offline storage, with a second protected copy under your control. Test that copy during a restore drill. Losing the private key makes the encrypted archives unrecoverable. Native X25519 recipients/identities only are supported; the tools do not invoke age plugins or SSH agents. No permanent recovery identity is generated by the tests.

## Create an export locally

Supply these variables through a secret manager or a mode-0600 environment file **outside the repository**. Do not put a database URL directly in a command, terminal history, or chat.

| Variable               | Purpose                                                                                                                                                                                                               |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `BACKUP_DATABASE_URL`  | Direct PostgreSQL URL. For remote sources use `sslmode=require` or `verify-full`; never `-pooler`. Prefer a dedicated least-privileged backup role that can read every public application table and export snapshots. |
| `BACKUP_AGE_RECIPIENT` | Operator-owned native age public recipient.                                                                                                                                                                           |
| `BACKUP_PG_BIN_DIR`    | Optional directory containing PostgreSQL 17 client binaries.                                                                                                                                                          |
| `BACKUP_OUTPUT_ROOT`   | Optional output directory. Defaults to the ignored `backup-output/` directory at the repository root.                                                                                                                 |

The URI accepts `sslmode`, `connect_timeout`, and the existing Prisma `schema=public`, `connection_limit`, and `pool_timeout` parameters. Prisma-only options are stripped before libpq runs; arbitrary libpq URL overrides are rejected. Connection credentials are passed through the child environment, not process arguments. `connect_timeout` is bounded to 15 seconds by the tool. Use the actual working direct connection; do not disable TLS or kill database sessions to bypass a routing failure.

```bash
# This file contains the backup-only variables, not the application's .env.
node --env-file=/absolute/private/path/backup.env ops/backup/cli.mjs create
```

Alternatively, inject variables and run `corepack pnpm backup:create`. The command does not automatically load dotenv files. It prints only a backup ID and table count. The new `excess-backup-<ID>` directory contains:

```text
database.dump.age
manifest.json.age
COMPLETE
```

Keep these three files together. Both data and manifest are encrypted; `COMPLETE` contains only the random backup ID. Do not upload partial output, plaintext dumps, private keys, or tool logs. Tool errors are deliberately generic because PostgreSQL/age errors can contain secrets or SQL data.

## Run a restore drill

Download a trusted complete backup to a private local directory. Start Docker, then supply a separate restore environment file containing:

```dotenv
BACKUP_DIRECTORY=/absolute/private/path/excess-backup-<ID>
BACKUP_AGE_IDENTITY_FILE=/absolute/private/path/backup.agekey
BACKUP_RESTORE_ACK=ISOLATED_LOCAL_CONTAINER
```

The private identity must be outside this repository, a regular non-symlink file, and mode 0600. The restore environment needs **no database URL or hosting credentials**. Select a local Unix-socket Docker context (Docker Desktop on macOS or local Docker on Linux); remote SSH/TCP Docker daemons and `DOCKER_HOST`/`DOCKER_CONTEXT` overrides are rejected. Every drill command is bound to that inspected socket so decrypted records are not sent to a remote Docker host.

```bash
node --env-file=/absolute/private/path/restore.env ops/backup/cli.mjs drill
```

The drill authenticates the manifest, checks the encrypted dump checksum, authenticates/decrypts the complete dump, creates a new disconnected container, prepares its empty database, and restores with `--single-transaction --exit-on-error --no-owner --no-acl`. It never uses `--clean` against an existing destination. Only the new disposable database's empty default `public` schema is removed before restoration.

Verification compares every public table's row count and SHA-256 content fingerprint with the **backup snapshot**, not today's changing live database. The encrypted manifest records both the source transaction's `snapshotAt` and the archive's later `createdAt`: use the snapshot time when assessing incident coverage. Decimal values stay in PostgreSQL's exact textual representation; no JavaScript money arithmetic is used. Account balances must equal their ledger totals, demo opening credits must match initial balances, and active failed/pending migration records are rejected. Migration-history rows/checksums, trade/position fields, and all other table data must match exactly.

Success prints `Restore drill verified` only after comparison and cleanup succeed. A failed comparison, failed decryption, failed restore, or failed cleanup is an unsuccessful drill. Record the trusted run/backup ID, archive creation time, drill time, table coverage, elapsed recovery time, and outcome in a **private** operations record. Do not publish counts/hashes from real customer data.

## Manual hosted-backup workflow: activation still required

Before activation, approve the encrypted storage location, retention, key custody, backup role, and failure-notification owner. The included workflow is **manual-only**; no cron job or scheduled automation is active.

1. Add a `database-backup` GitHub environment and restrict it to `main`. Consider required reviewers where available. The workflow also checks the exact repository and branch.
2. Add the direct source URL as the `BACKUP_DATABASE_URL` **secret** in that environment. Do not copy it into workflow YAML. Prefer a dedicated read-only backup credential rather than the broad application-owner credential. Provisioning such a role is a separate reviewed database change.
3. Add `BACKUP_AGE_RECIPIENT` as an environment/repository **variable**. Verify it against the identity kept outside GitHub. Do not add any `AGE-SECRET-KEY` value as a secret.
4. Decide whether GitHub Actions artifacts are acceptable for **encrypted** retention. Treat artifacts in this public repository as publicly obtainable ciphertext, not confidential storage. The sample keeps only the three allow-listed files for **30 days**. This is short-lived operational storage, not an independent long-term/offsite backup. Artifact expiration, account loss, deletion, and quotas can remove recovery points. Approve and configure a separate durable destination before relying on a recurring policy; never make an unencrypted fallback upload.
5. Only after those choices, set `BACKUPS_ENABLED=true`. Run **Encrypted database backup** from `main`. Activation absent or incorrect fails visibly rather than reporting a successful backup.
6. Download the resulting artifact, check the repository/run provenance, and run the local drill using the separately stored private identity. A green backup job proves export/encryption/upload, **not** a tested restore.
7. Keep GitHub Actions workflow-failure notifications enabled for the operator in GitHub notification settings, including failed runs triggered by that operator. Verify the delivery channel with a harmless misconfiguration before trusting notifications. Job summaries identify failures without exposing SQL or credentials. No independent alert-delivery integration or missing-schedule/staleness alarm is configured yet.

Do not enable a schedule until one real hosted export and local restore have passed, the notification path is tested, and offsite storage/retention is approved. A future proposed demo policy is a daily recovery point plus a periodic restore drill; it is not a promised RPO or an active schedule. Define an RTO only after measuring recovery on the actual backup size.

## Real incident recovery: separate from the drill

The tool intentionally has no live restore mode. A real recovery requires explicit operator approval and a reviewed maintenance plan:

1. Pause releases and application writes; preserve the damaged source for investigation. Identify the incident time and select a **pre-incident, verified** recovery point. Recognize that writes after its snapshot are not present.
2. Check key custody, backup provenance, age authentication, schema/application compatibility, and the recorded drill result. Run another isolated drill if practical.
3. Provision an approved **new empty** database, with reviewed costs/capacity. Do not overwrite or drop the live database and do not repoint the app to the drill container.
4. In maintenance, restore the trusted archive using a reviewed direct connection, validate all data and migration history, rebuild appropriate roles/grants, and verify application read/write behavior with an isolated identity. Keep notification/outbox consumers disabled until the replay/delivery implications are reviewed.
5. Switch application connection secrets only after validation. Check readiness, authentication, account balances, ledger, trades, and positions; then resume writes and monitor. Retain the original database and documented cutover decision until recovery is accepted. Do not down-migrate financial records or automatically merge post-snapshot trades.

## Development verification

```bash
corepack pnpm test:backup
corepack pnpm test:backup:integration
```

The integration test creates **synthetic** data in a new loopback-only fixture container, applies all committed migrations, generates temporary test keys, and performs real encrypted exports/restores. It tests concurrent source commits, exact decimal/position/migration preservation, wrong keys, damaged/truncated or incomplete output, data mismatches, financial reconciliation failures, and cleanup. It never loads the hosted database URL, changes live records, or uploads any backup/test artifacts. CI runs it as a separate job without hosted credentials.
